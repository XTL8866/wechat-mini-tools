# 文本润色

一段话，四种改法：精简、扩写、口语转书面、改写降重。纯本地运行，不联网、不登录、不上传输入内容。

系列第二个工具，一天一个。

## 功能

- **精简**：删填充词（其实 / 基本上 / 我个人觉得）→ 压冗余句式（对流程进行优化 → 优化流程）→ 合并重复片段 → 整理标点。减幅不到 12% 时再删一层程度副词
- **扩写**：句间补连接词，短句补一句按关键词生成的展开句。全篇最多补三句，接近字数上限就只补连接词
- **口语转书面**：口语词表替换（我觉得 → 笔者认为、挺 → 较为、搞 → 开展），删句末语气词，感叹号转句号
- **改写降重**：同义词替换（同一词条只用一次）+ 把字句转将字句 + 状语后置，种子可复现
- 每条结果都给**改动清单**：改了哪些词、换成什么、一共几处
- 字数对比：`77 字 → 63 字 · 少 14 字`；等长换词时改报「4 处改动」
- 免费 2 次，激励视频解锁后不限次
- 1000 字上限，超了提示分段

## 跑起来

**小程序**

1. 打开微信开发者工具 → 导入项目 → 选 `02-text-polish` 目录
2. AppID 选「测试号」即可（`project.config.json` 里是 `touristappid`）
3. 编译，直接可用

**逻辑自测**

```bash
node test.js     # 36 项断言，覆盖空输入、超长、边界字数、去重、种子可复现
```

**浏览器预览**

直接用浏览器打开 `preview/index.html`。它引用同一份 `core/polish.js`，只换渲染层，所以界面和真机一致。

## 广告位

`core/ads.js` 顶部有一个常量：

```js
var AD_UNIT_ID = '';   // 拿到流量主后填这里
```

**现在是空的，这是有意的**。新小程序没有流量主权限（需累计独立访客 ≥1000），此时填任何 ID 都会触发「广告拉取失败」。所以代码做了降级：拉不到广告 → 视为解锁成功，直接放行。

拿到流量主后，把真实 `adUnitId` 填进这个常量，其余代码不用动。banner 同理，`pages/index/index.js` 里的 `adUnitId` 为空时 `<ad>` 组件不渲染。

## 页面结构

单一页面 `pages/index`：

| 区块 | 说明 |
|---|---|
| 原文 | textarea，1000 字上限，改字清空旧结果 |
| 改法 | 四个 chip，切换后清空结果 |
| 主按钮 | 无结果时「开始润色」，有结果时「再跑一次」 |
| 结果 | 改后正文 + 字数变化 + 改动清单 + 复制 |
| 解锁 | 免费 2 次之外的部分 |
| banner | 未配 ID 时不渲染 |

## 已知限制

- 规则法不是语义法。能处理水词、冗余句式、口语词、同义词，处理不了「这句话逻辑不通」
- 精简只删不改写，遇到本身就很紧的句子会给出「已经很紧凑」提示，不会硬凑减幅
- 扩写的展开句是模板 + 关键词回填，关键词可能抽成「这件事」兜底
- 改写降重的同义词表 36 条，每个词条在一次处理中只用一次，重复段落多的时候会不够用
- 没有历史记录，不存草稿

## 设计取舍

**为什么不做成 AI 改写**：需求是本地跑、不登录。接大模型要密钥、要后端、要计费，还要处理超时和内容审核。规则法的上限低，但每条改动都是可验证的字符串操作——能列出来给用户校对，这比不可解释的「AI 帮你改好了」更实用。

**为什么改写要带种子**：同一段文字跑两次应该给出两版，而不是每次都一样。用种子控制随机性，既能换出不同版本，也能在测试里复现同一结果。

**为什么删程度副词放在第二层**：`非常` `确实` 这些删了会让语气变弱。只有在水词删完、减幅仍不到 12% 时才动它们，避免好好的文章被削成简报。
